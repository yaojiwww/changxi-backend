# Dify 侧配置说明：让 AI 结合「选中的知识点」回答

> 读者：负责 Dify 应用编排的同学
> 适用：Dify Cloud / 自建 Dify 1.x，应用类型为聊天助手（Chatbot）、智能体（Agent）或聊天流（Chatflow）
> 目标：用户在 App 里选中一个章节后，AI 优先结合该章节的知识库内容回答；用户不选时行为与现在一致

---

## 0. 这次要达成的效果

改造前：用户想问某一章的内容，只能把知识库原文手动粘贴到聊天框里。

改造后：

1. 用户在 App 里选中章节（例如「中级 · 组织进餐」）
2. 后端查出章节展示名，随请求传给 Dify
3. Dify 用章节名做检索提示，从知识库里取这一章的内容
4. AI 基于检索结果回答，用户不需要再粘贴任何原文

知识内容只在 Dify 知识库里维护一份，后端和前端都不再拼接知识库正文。

---

## 1. 与后端的接口契约（不要改）

后端调用的是 Dify 的 `POST /v1/chat-messages`，请求体如下：

```json
{
  "inputs": {
    "mode": "solve",
    "kpName": "中级 · 组织进餐"
  },
  "query": "【当前知识点：中级 · 组织进餐】\n进餐时应该先做什么？",
  "response_mode": "streaming",
  "conversation_id": "上一轮的会话ID，首轮为空串",
  "user": "登录用户ID"
}
```

字段说明：

| 字段 | 说明 |
|---|---|
| `inputs.mode` | `solve`（题目解答）或 `plan`（专属规划），可能为空串。这是原有变量，保持不变 |
| `inputs.kpName` | 当前选中的章节展示名，例如 `中级 · 组织进餐`。**没选中时是空串，但每轮都会传** |
| `query` | 用户问题。选中章节时，后端会在最前面加一行 `【当前知识点：章节名】`，后面跟用户原话 |
| `conversation_id` | 多轮记忆用。首轮空串，之后由前端带回上一轮的 ID |
| `user` | 用户标识，用于隔离不同用户的多轮记忆 |
| `response_mode` | 固定 `streaming`，后端是按 SSE 增量转发的，**不能改成 blocking** |

后端只转发 Dify 返回的四类内容：`event`、`answer`、`conversation_id`、`message`。因此：

- 应用必须保持流式输出
- 不要改成只返回自定义结构化结果、不产生 `message` 事件的工作流
- `message_end` 事件必须照常产生，后端靠它判断本轮结束

## 2. 在应用里定义输入变量 `kpName`

进入 Dify 应用 → 编排 → 左侧「变量」面板 → 新增变量。

| 配置项 | 值 |
|---|---|
| 变量名 | `kpName` |
| 类型 | 文本 / String |
| 默认值 | 空 |
| 是否必填 | 否（关闭） |
| 最大长度 | 128 足够 |

注意事项：

1. **变量名必须一字不差是 `kpName`**，大小写敏感。Dify 对未定义的输入变量是静默忽略的，名字拼错不会报错，只会表现为「回答完全没变化」，非常难排查。
2. `mode` 变量是之前就有的，确认它还在，不要删。
3. 后端每轮都会传 `kpName`，所以 prompt 里只需要判断「是否为空」，不需要处理「变量不存在」的情况。
4. 定义完变量后，在调试面板里应该能看到 `kpName` 输入框。可以手动填一个章节名做验证。

验证方法：调试面板填入 `kpName = 中级 · 组织进餐`，提问后看回答是否围绕该章节。如果没变化，先检查变量名。

## 3. 知识库配置

### 3.1 资料准备

先把知识内容整理成适合检索的文档：

- 每个章节单独一个文档，文件名建议 `{kpId}_{章节名}.md`，例如：
  - `kp-basic-law_相关法律法规及其它试题.md`
  - `kp-beginner-water_组织饮水.md`
  - `kp-intermediate-meal_组织进餐.md`
  - `kp-advanced-sleep_组织睡眠.md`
- 文档里的标题必须包含章节名。后端注入的检索提示就是章节展示名，标题里出现同样的词，召回率会明显更高。
- 删除页眉页脚、页码、重复的表格线，这些东西会变成无效 chunk。
- 同一份资料里不要混多个章节；如果原始 docx 是一整本，按章节拆开再导入。
- 术语与 App 里保持一致（例如统一叫「组织进餐」，不要一半写「进餐组织」）。

### 3.2 导入与分段

Dify → 知识库 → 创建知识库 → 导入文档。

分段建议（按资料形态选一种）：

| 资料形态 | 分段方式 | 参数建议 |
|---|---|---|
| 普通章节正文 | 通用分段 | 最大分段长度 500～800 tokens，重叠 50～100 tokens，分隔符优先用空行/标题 |
| 一问一答的题目解析 | Q&A 分段 | 问题和答案成对导入，问题里保留章节名 |
| 长文档、版本支持父子分段 | 父子分段 | 父块保留小节上下文，子块用于精确召回 |

索引方式：

- 选「高质量」（向量索引），不要用「经济」
- Embedding 模型必须支持中文（例如 bge-m3、中文优化的 embedding 模型）
- **建好索引后不要随意换 embedding 模型**，换了必须重建索引，否则检索结果会整体变差

### 3.3 挂载到应用并设置检索

应用 → 知识库 → 添加 → 选择上面建好的知识库。

检索设置建议（先按这套跑通，再按实测调）：

| 配置项 | 建议值 | 说明 |
|---|---|---|
| 检索模式 | 混合检索 | 向量 + 关键词，章节名属于关键词，混合检索对中文专有名词更稳 |
| 向量权重 / 关键词权重 | 0.7 / 0.3 起步 | 如果章节名经常召不回，把关键词权重调到 0.4～0.5 |
| TopK | 4 | 3～5 之间；太大容易混入其他章节 |
| 相似度阈值 | 0.5 起步 | 召回不到就降到 0.4；混入无关内容就升到 0.6 |
| Rerank | 有就开 | 用中文 rerank 模型，能明显改善「同一章内容太多」的场景 |

⚠️ 关于元数据过滤：`chat-messages` 接口目前不支持按请求传检索过滤条件，所以**不要指望用元数据按 kpId 过滤**。章节聚焦靠的是 query 里的 `【当前知识点：…】` 前缀，这是当前方案的关键，不要去掉。

### 3.4 验证检索是否命中

在应用调试面板里，用带前缀的问题测试：

```text
【当前知识点：中级 · 组织进餐】进餐时应该先做什么？
```

提问后打开「引用」/「检索结果」面板，确认：

- 召回的 chunk 来自「组织进餐」文档
- 没有大量混入「组织饮水」「组织睡眠」的内容
- 如果召回了空结果，先检查文档是否挂到应用、阈值是否太高、标题里有没有章节名

## 4. 提示词配置

### 4.1 原则

下面是**增量规则**，合并进现有系统提示词即可，不要整段覆盖原有的 `mode`（solve/plan）逻辑。

`kpName` 请用编辑器的「插入变量」功能选择，不要手打。不同 Dify 版本插入后的语法可能显示为 `{{kpName}}` 或类似形式，以编辑器实际插入结果为准。

### 4.2 可直接合并的提示词片段

```text
# 当前上下文
- 提问模式：{{mode}}
- 当前知识点：{{kpName}}

# 知识点使用规则
1. 当「当前知识点」不为空时：
   - 优先使用知识库中与该章节相关的内容回答，回答要落到该章节的具体要求、步骤和注意事项上。
   - 回答中应体现你依据的是该章节资料，例如「在组织进餐这一章中……」。
   - 如果知识库里没有该章节的相关内容，明确说明「知识库中暂未收录该章节资料」，再给出通用建议，不要编造具体条款、数字或步骤。
2. 当「当前知识点」为空时：
   - 按普通问答处理，不要主动引入章节概念，也不要强行说「本章」。
3. 用户问题最前面可能出现一行「【当前知识点：…】」：
   - 那是系统注入的检索提示，不是用户原话。
   - 不要复述这一行，也不要把方括号里的内容当作问题的一部分。
4. 回答依据：
   - 知识库有内容时，以知识库为准；知识库没有时，明确区分「通用建议」和「知识库内容」。
   - 不要要求用户再粘贴知识库原文。
5. 输出风格：
   - 面向手机端阅读，短段落、要点式表达。
   - 避免复杂表格和超长代码块。
   - 单次回答控制在 300～600 字，除非用户明确要求展开。
```

### 4.3 与原有 mode 逻辑的衔接

原有提示词里如果已经有 `solve` / `plan` 的分支，保持不动，只把上面「知识点使用规则」插在角色设定之后、输出格式之前。两者不冲突：

- `mode=solve`：题目解答，仍然先解题，但涉及知识点时优先引用 `kpName` 对应章节
- `mode=plan`：学习规划，可以把当前章节作为规划范围的一部分
- `mode` 为空：按通用问答处理

### 4.4 一个示例（可放进提示词的 few-shot）

```text
示例：
当前知识点：中级 · 组织进餐
用户问题：【当前知识点：中级 · 组织进餐】进餐时应该先做什么？

期望回答风格：
在「组织进餐」这一章中，进餐环节的重点是……（引用知识库内容）
具体步骤是：1. …… 2. …… 3. ……
如果知识库没有覆盖你问的这一点，我会明确说明。
```

## 5. 多轮对话与章节切换

- `conversation_id` 让 Dify 记住同一轮对话的历史；`kpName` 是**每轮独立传的**，不是会话级变量。
- 用户在同一会话里切换章节时，前端会新开一个 `conversation_id`。如果前端没新开，提示词里的「当前知识点」应优先于历史上下文，这一点已经在第 4 节规则里写明。
- 建议在应用设置里把「上下文轮数」控制在 3～5 轮。知识库 chunk 本身占 token，轮数太多会挤压回答空间。
- `user` 字段已经按登录用户隔离，不要改成固定值，否则不同用户会共用多轮记忆。

## 6. 测试与验收

### 6.1 Dify 调试面板

1. 设置 `kpName = 中级 · 组织进餐`
2. 输入 `【当前知识点：中级 · 组织进餐】进餐时应该先做什么？`
3. 检查回答是否围绕该章节
4. 打开引用面板，检查召回来源

### 6.2 直接调 Dify 接口（不经过后端）

用应用的 API Key（不是知识库的 Key）：

```bash
curl -N -X POST 'https://api.dify.ai/v1/chat-messages' \
  -H 'Authorization: Bearer app-xxxxxxxx' \
  -H 'Content-Type: application/json' \
  -d '{
    "inputs": {"mode": "solve", "kpName": "中级 · 组织进餐"},
    "query": "【当前知识点：中级 · 组织进餐】进餐时应该先做什么？",
    "response_mode": "streaming",
    "conversation_id": "",
    "user": "test-user"
  }'
```

自建 Dify 把地址换成 `http://<host>/v1`。返回里应能看到 `event: message` 和逐段 `answer`，最后有 `message_end`。

### 6.3 验收用例

| 编号 | 请求 | 期望结果 |
|---|---|---|
| 1 | 不传 `kpId`，后端发出的 `kpName` 为空串，query 无前缀 | 与改造前表现一致，回答不强行提章节 |
| 2 | `kpId = kp-intermediate-meal`，问「进餐时应该先做什么」 | 回答落到「中级 · 组织进餐」，引用面板能看到该章节文档 |
| 3 | 选一个知识库没有资料的章节 | 明确说明资料缺失，不编造具体内容 |
| 4 | 同一会话连续追问两轮，章节不变 | 第二轮沿用同一 `conversation_id`，仍然围绕该章节 |
| 5 | 连续追问中途切换章节（新开会话） | 回答切到新章节，不把旧章节内容带过来 |

### 6.4 常见问题排查

| 现象 | 优先排查 |
|---|---|
| 回答完全没变化 | `kpName` 变量名拼错 / 没定义 / 应用没发布 / 后端没重启 |
| 变量面板里 `kpName` 为空 | 后端没重启，或请求体没带该字段；用 6.2 的 curl 直接验证 |
| 选中的章节检索不到 | 文档没挂到应用 / 阈值太高 / 标题缺章节名 / embedding 模型不支持中文 |
| 回答混入其他章节 | TopK 太大 / 阈值太低 / 文档没按章节拆分 / 关键词权重太低 |
| 回答泛泛而谈 | prompt 没引用 `kpName`，或知识库内容为空，模型退回了通用知识 |
| Agent 应用有时不检索知识库 | 智能体是模型自主决定是否调用知识库；需要在指令里强调，或改用 Chatflow 固定一个知识检索节点 |
| 多轮后串到旧章节 | 切换章节时没新开 `conversation_id`，或 prompt 没写「当前知识点优先于历史」 |

## 7. 发布与交付清单

改完编排后，Dify 侧需要「发布」应用，API 调用才会用新配置。发布前逐项确认：

- [ ] 输入变量 `kpName` 已定义，类型为文本，非必填
- [ ] 原有 `mode` 变量仍然存在
- [ ] 四个章节的知识库文档已导入并挂载到应用
- [ ] 分段、检索模式、TopK、阈值已按第 3 节配置
- [ ] 提示词已加入「知识点使用规则」，且没有覆盖原有 mode 逻辑
- [ ] 用调试面板 + curl 各验证过一遍
- [ ] 6.3 的五个用例通过
- [ ] 应用已发布
- [ ] 确认仍使用同一个 API Key（后端从环境变量 `DIFY_API_KEY` 读取），接口地址仍是 `DIFY_API_BASE`
- [ ] 确认返回仍是 `streaming`，有 `message` / `message_end` 事件
- [ ] 把知识库 ID、分段参数、提示词版本记录到项目文档，方便回溯

---

## 8. 不要做的事

1. 不要改 `kpName`、`mode` 这两个变量名，后端是按名字传的。
2. 不要把 `response_mode` 改成 `blocking`，后端是按 SSE 增量转发的。
3. 不要把知识库正文塞进 `inputs` 或让用户手动粘贴，知识内容统一在知识库里维护。
4. 不要依赖 `inputs` 触发知识库检索——检索只看 `query`，章节名前缀是当前方案生效的关键。
5. 不要在 prompt 里写死某一道题或某一年的答案，回答必须以知识库检索结果为准。
6. 不要把后端传的 `user` 改成固定值，否则所有用户会共用多轮记忆。
